# Shift Plan (SSS)

Support-floor coverage calendar. One HTML file. The live page is https://shift-plan.autoleap-sss.workers.dev/ (Google sign-in required) and the header reads **Shift Plan**. The old GitHub Pages address, https://osaid-ak.github.io/sss/, only redirects there.

Read this file before changing the calendar. Update it in the same change when behavior, publish steps, or standing rules change.

## Files

- `coverage-calendar.html` is the working copy. It is not committed.
- `index.html` is only a redirect to the worker address (a copy of `worker/stub-index.html`). It no longer matches the working copy. Never put the calendar back into it: GitHub Pages is public.
- `serve-calendar.py` is a local server only. Do not commit it.
- `README.md` is the short tester note. Keep it consistent with this file.

## Publish

1. Edit `coverage-calendar.html`.
2. In the `worker` folder run `.\deploy.ps1`. It builds the protected copy (plan address and `SSS_GATED` swapped in) and uploads the worker.
3. Commit `AGENTS.md` and anything else that changed (the calendar file itself is not committed), then push `main`. Do not touch `index.html`.
4. Tell the user to hard-refresh with Ctrl+F5 on the worker address.

Test with a copy of the calendar pointed at a local stand-in (see "How the data is shared"), then deploy. Do not commit `coverage-calendar.html`, `serve-calendar.py`, `worker/seed-plan.json`, or secrets. On PowerShell, commit with `git commit -m "..."` and chain commands with `;`.

## Sign-in gate (Cloudflare Worker, in `worker/`)

Access is restricted to people on the allowed email list, who sign in with Google (Intercom sign-in was dropped: it is an app-install flow that regular teammates cannot authorize). The worker serves the calendar page and stores the shared plan in a Durable Object (`PlanStore`, one strongly consistent copy; mantledb is no longer used by the gated site because it went down once); nothing is served before sign-in. Secrets (Google client ID and secret, session secret, allowed emails, admin emails, Super Admin email) are Cloudflare secrets, never in the repo or in chat. `worker/README.md` has the setup. `worker/deploy.ps1` builds `worker/public/index.html` from `coverage-calendar.html` (swapping the plan address for `/api/team/plan` and setting `SSS_GATED = true`, which also makes the page send the plan in one piece) and deploys; `worker/public/` is not committed. Run `node worker/test.mjs` after changing the worker.

Roles when gated: Member (no Access button, no lead tools), Admin (lead access without the PIN, plus Users under Access to add people as Members, remove Members and change Members' roles; added and removed people are kept in the ROLES store on top of `ALLOWED_EMAILS`) and Super Admin (one person; the only one who can add an Admin or change or remove an Admin). Everyone signed in gets a Sign out button in the header. Sessions are signed cookies (7 days), not a server-side list; each deploy sets a new `BUILD_ID` (`deploy.ps1` passes it with `--var`) that is inside the cookie, so every deploy signs everyone out and they sign in with Google again (an open tab goes straight to the sign-in page within about 15 seconds: the page wraps etch so any own-API call that answers 401 redirects to /, and a 15-second /api/me check also runs when the tab becomes visible; the stale cookie is cleared; the activity log gets one "deploy" line by System when the first old session is met, and a "session ended" line with the person's name and email as each one is). Local data in the browser (the plan copy, backups, theme) is not a cookie and is kept; the worker keeps an activity log of the latest 1000 events (sign-in, refused sign-in, sign-out, user added, removed or role changed, and every schedule edit) in the ROLES store, readable by Admins under Access > Activity log. Every entry carries the person's name (made from their email, for example muhammad.jawad becomes Muhammad Jawad) and email. Schedule edits are worked out on the server on every plan save by comparing the new plan with the stored one, so they are logged whoever or whatever sends them: roster changes, hours and break changes, role changes, leave requests and their approval, decline or cancellation, holiday plans created, changed or deleted, late-shift and Phase 1 cover added or removed, and a weekday edited by hand or reset to default. Data that comes from the Google Sheet (VIP blocks, Support Line rotation and hours, Saturday names) is never logged as an edit, nor are roster hours taken from the sheet's original shifts. An import or restore shows as one Large change line. One limit: a save is attributed to whoever's browser sent it, so edits another person made offline and that were merged in by a later save are credited to that later sender. Each entry holds email, event, time, country, IP address and browser (User-Agent, shortened to 200 characters); these are personal data of teammates, so only Admins can read them and they are never shown to Members. The log has a search box that filters live from 2 characters on (several words must all match) across everything shown in a row: time, event, email, detail, IP, browser, country. The panel shows a short label such as "Chrome on Windows" with the full browser string on hover. The IP and browser fields are there so a future mobile app's sign-ins can be told apart. The server decides the role (`/api/me`) and enforces role changes. `SSS_GATED` stays `false` in the committed file; the PIN flow still applies to the ungated GitHub Pages copy.

The gate is live: the calendar and the plan are only served after Google sign-in, the plan is stored in the worker, and `index.html` on GitHub Pages is a redirect. A browser with no plan of its own shows "No team plan yet" (never the starter data) when the store is empty, and an Admin starts it with Import plan file. Still open: the old mantledb plan is public and in the git history, so overwrite it with an empty placeholder once mantledb is reachable and everyone has reloaded; making the repo private is optional.

## Read API for automations (Intercom team moves)

`GET /api/v1/intercom-plan?from=YYYY-MM-DD&days=N` on the worker (`worker/src/intercom.js`, route `automationApi` in `worker/src/index.js`). It uses an API key (`Authorization: Bearer`), not a Google sign-in: the secret `API_KEYS` holds comma-separated `label:key` pairs (one per automation, removing a pair revokes it; keys are compared as hashes, never logged or returned; a refused call is logged as "api refused", at most once every 10 minutes). It is read only, never cached, and has no Intercom token: the Intercom automation (a separate Cloud Run project) stays the only writer. It does not follow the Google sign-in, the build-id session end or the roles.

It reports per shift day (the date it starts on, 15:00 PKT to 15:00 PKT) only the *decisions* leads made: people whose Phase 1 / VIP queue differs from normal (roster queue, with the sheet rotation's Phase 1 person on Phase 1, Monday to Friday). Sources, in the page's own order: the stored roles of a hand-edited weekday, then late shift cover (`vip`, `phase1`) and the Phase 1 queue cover (`p1q`). A Saturday has no rotation and nobody moves unless the Weekend Cover names them: everyone it names is a decision with that queue (the rotation person goes to VIP only if named as a VIP rep, otherwise stays on Phase 1). Sunday never has decisions. Every call reads the Weekend Cover and VIP Coverage Plan tabs from Google itself (`worker/src/sheets.js`, the page's own reader, compared with it on the live tabs; the sheet must be readable by link) so nothing depends on an open browser, falling back per tab to the plan's stored copy and saying so in `sources`. Each day also carries `queues`, the calendar's full picture (every roster person's queue, rotation included; null on a Sunday), used only as a cross-check: the automation acts on `decisions`, on top of its own live sheet read (sheet = intended state, the calendar's changes win, hourly, acting on changes; see `handoff/intercom/README.md`). Decisions and the roster carry an `email` (the roster entry's own `email` field, else the one allowed email containing the name, else null) so the automation can verify the Intercom ID before moving anyone. `sheets.js` must be kept in step with the page's `parseWeekendRows` / `parseVipPlanRows` / `parseAnyDate`. Each day also carries who is off (`away`), who covers whom with exact times (`covers`, the same sentences as the page's Covering tonight box), what still needs a lead (`needsCover`, the page's red alerts) and the block's Late Shift person (`lateShift`), worked out by `worker/src/covers.js`, a function-by-function port of the page's `resolveDay`, `coveringFor`, the late-shift/anchor/Support Line logic and the leave and holiday rules; it also reads the Phase 1 / Support Line tab live (`parseSheetTab` in `sheets.js`). Any change to those page functions (or to `parseWeekendRows`, `parseVipPlanRows`, `parseSheetPlanRows`, `parseOriginalRows`, `parseAnyDate`) must be mirrored there and re-verified by comparing the worker with the page in the browser: build a test copy of the calendar with the worker modules bundled in and the page's `resolveDay` / `coveringFor` exposed, then compare covers, away and the lead alerts (read from the rendered day view) over a real plan and over randomised plans (leave, holidays, late/queue/anchor covers, hand edits, Support Line rotation, shift hours), across a clock change. The last run (13 plans, about 1,900 covers of all five kinds) had no differences. Anything that changes the queue logic in `resolveDay` / `applyLateCover` / `applyVipBlock` must be mirrored in `dayPlan` (`worker/src/intercom.js`) and checked against the page again (the `worker/test.mjs` API checks, plus comparing `dayPlan` with `resolveDay` over a real plan in the browser). `handoff/intercom/` is the package for that other project (contract, tested Python module, rollout); keep it in step with the API.

## Commands that change the calendar (Slack `/calendar`)

Leads change the calendar from Slack with `/calendar ...` (the Slack bot lives in the separate Intercom Phase Assignment project; `handoff/slack-calendar/` is its brief, with the JSON schema and 29 golden phrases that the worker's tests run). The worker does the work: `worker/src/commands.js` (validate, preview, apply, undo), `worker/src/dates.js` (dates in words, deterministic: `20th Nov to 25th Nov`, `from coming Monday to Thursday`, `this week and next`, ...), and the routes `POST /api/v1/calendar/command` and `/api/v1/calendar/undo` in `index.js`. They use a **write key** (secret `WRITE_KEYS`, same `label:key` format as `API_KEYS`; a read key cannot write and a write key cannot read) plus the asker's email (`actor.email`), and the asker must be allowed in AND an Admin or the Super Admin (checked again on the server). A request is a **preview** unless it says `dryRun: false`; applying needs a `commandId` (a repeat returns the stored result, nothing twice) and may carry the preview's `previewHash` (a mismatch applies nothing). The write is conditional on the plan version it was made from (`X-Expect-Updated-At`, retried up to three times), so it never overwrites a browser's save. Each command's undo record and result are kept in the plan store (`kv/undo-<id>`, `kv/cmd-<id>`), and `/calendar undo` takes back exactly what it added. The Google Sheet is never written, by anything.

What it writes, only for the nights named: approved **leave** (`off`; `back` splits and cancels), the calendar's own cover slots (`lateCover` late / Phase 1 / `p1q` / `anchor`), and **per-night changes** in the plan as `changes[date] = [{ id, cmd, type, ..., by, via, at }]`: `queue` (works Phase 1, VIP or both), `shift` (late shift, an anchor, or hours), `takeover` (works another person's queue and shift, optionally a named shift such as the 6pm anchor: that also fills the anchor the covered person left) and `swap` (two people exchange shifts and queues). They are applied last when a night is built (`applyChanges`, after the sheet, the block, the covers), on top of hand-edited nights too, and never change the roster. A night a lead hand-edits keeps the changes it already shows (`baked` ids), so a swap is never applied twice; "Reset this day to default" brings them back from the plan. Leads see each change under the day's alerts as "Moved by <name> via Slack: ..." with a Remove button; everyone sees "(moved)" / "(covering)" and the Covering tonight sentences; anything still open is shown by the usual red Lead action alerts (a moved anchor person's open anchor, a late shift without a Phase 1 person, ...). Shifts and swaps are refused on Saturdays (the Weekend Cover sheet rules them; marking someone off on a Saturday is allowed and says the spot needs a name on the sheet), Sundays and past nights are skipped, leads are not used as cover, a person who is off cannot cover, and one person never gets two jobs a night. The activity log records `calendar command` and the individual `plan edit` lines under the asker's name with `via: Slack` (the lines are never collapsed to "Large change").

`dayPlan`, `covers.js` and `commands.js` mirror the page's `applyChanges`, `anchorGaps` / `gapCover` and `coveringFor`; the page and the worker were compared over randomised plans with every change type (about 2,200 covers, 9,500 queue checks, no differences, across the clock changes). Re-run that comparison after changing any of them (see the Read API section).

## How the data is shared

All three tabs are read by one JSONP reader (`fetchGvizRows`); the old Apps Script and same-origin weekend fallbacks are gone. Sheet updates and hand edits: the page re-reads all three sheet tabs when it opens, every 45 seconds while the tab is visible, as soon as the tab becomes visible again, every 20 seconds while the Shift Sheet panel is open, and when that panel closes (so a change on the sheet shows within about a minute on every open calendar, and the shared plan then carries it to the others). A weekday a lead has saved is a snapshot of that whole day (this also happens when a lead copies a day, applies a roster hours change to a whole month, or confirms holiday hours, not only when a day is dragged by hand); its other shifts, breaks and roles stay as saved. **Late shift and Phase 1 coverage always follow the sheet on saved nights from next week on** (`followsRotation`: the night is saved, it is a weekday, and it is on or after the Monday after this week; this week is left as saved): the block's Late Shift person, its Phase 1 person and its Anchor Cover people are rebuilt from the sheet for that night's own block (`followRotation`, `rotationBase`), and so are the people who were on the rotation when the night was saved (`day.rot`; for nights saved before that was recorded, whoever works the late hours, sits on Phase 1 against their roster queue or works a vacated anchor's hours), who go back to their usual shift. The anchor alerts, the Phase 1 queue need and the "(Late Shift)" / "(Phase 1 Coverage)" tags work on those nights too (only for the block's own people; covers and commands are already part of what was saved). The exception is a person edited directly on that night (`day.touched`: dragging their bar or break, splitting, toggling a role, holiday hours, a leave suggestion applied, or a command already built in): they stay as edited and carry no rotation tag, and the rest still follows the sheet. Copying a day copies the other shifts; it never copies the source's `touched`, and it never overwrites what a lead edited directly on the target night (those people and their `touched` marks are kept; the dialog and the toast say so), and the rotation people of the source are rebuilt from each target night's own block (the copy stamps `rot` with the source's rotation people). The day view tells leads "Saved as edited" with a Reset this day to default button (outside edit mode it asks first and offers Undo). The worker mirrors all of this (`covers.js` and `storedPeopleFor`, used by `dayPlan`). Saturdays are the exception: the names come from the Weekend Cover sheet and the shift hours are always rebuilt from the product windows, so a hand edit to a Saturday's hours is not kept. Leave, holiday plans, roster edits and covers a lead added are never touched by the sheet.

Edits sync through the shared plan named `TEAM_PLAN` in the calendar file. A browser also keeps a local copy. Do not describe the calendar as Export/Import only.

Removing someone from the roster records them in the plan's `removed` list (name and time). Every merge and load drops those names from the roster, the default Support Line bars and hand-edited weekdays, so an older copy in another browser cannot bring them back (the three-way merge alone would, when that browser has no sync base). Adding the same name again clears the entry. Saturdays follow the Weekend Cover sheet, so a name still on that sheet still shows on Saturdays until the sheet is changed; leave history stays.

Safety rule: a browser that has no plan of its own must adopt the team plan exactly on first contact, and data read from the Google Sheet (weekend names, VIP blocks) is saved quietly without counting as a team edit. Never let anything bump `updatedAt` or push before the first team sync finishes, because built-in default names and hours would then overwrite the team's roster. When testing, never load the live page from a fresh browser such as the preview pane. Use a copy pointed at a local stand-in for the team plan.

Each browser keeps up to 5 automatic backups (local storage key `coverage-calendar-backups`), taken before a teammate or merged update (at most every 15 minutes) and before a JSON import or restore. Lead tools has Restore backup. Import asks for confirmation because it replaces the shared plan. Browser panes that block storage skip backups silently.

Always read the Actual Cover columns on the sheet, not Planned. Actual updates itself when a swap happens. Swap, then Planned, only fill in when Actual is blank. Saturday names come from the Weekend Cover sheet. On Saturdays the Phase 1 rep works the full 6 hours with no break (stored as a break just past the shift end, which the page does not draw or count), and the VIP reps never break together: the first at the middle of the shift, each next one an hour later, in the order the sheet lists them. The sheet has no time columns. The product windows are Phase 1 8pm–2am and VIP 5pm–2am. Display re-applies those windows, then adds one hour on standard-time dates. Do not make that spreadsheet world-editable. Do not rewrite stored clocks unless the user asks.

The `2. VIP Coverage Plan` tab (gid 1563923804, same workbook) lists two-week Monday to Friday blocks. Each block names one VIP person on Late Shift and one on Phase 1, read from Actual Cover, plus the two anchor cover names from the Anchor 1 and Anchor 2 columns. The page polls it with the weekend sheet and stores the blocks in the shared plan as `vipPlan`. On weekdays inside a block, the Late Shift person works 9:30pm–6:30am PKT (10:30pm–7:30am on standard-time dates), keeping their usual break offset, and the Phase 1 person moves from VIP to Phase 1 for the whole shift. Days someone edited by hand keep their own edit. Saturdays and Sundays are not affected. A failed read keeps the last blocks.

Every weekday late shift (anyone starting at 9:30pm PKT, or 10:30pm on standard-time dates, or later) needs one working VIP person and one working Phase 1 person. People who are Off or PTO do not count. When one is missing, the day view shows a red alert above the timeline naming who is off, and the month and week cells for that day show the red gap tint. With lead access the alert has a dropdown and Add cover button. Phase 1 queue cover is separate from the late shift: if the Phase 1 person the VIP Coverage Plan names is off, the day shows a Phase 1 needs cover alert and the Lead action highlight until a lead adds a VIP rep to Phase 1 (stored as `p1q` in `lateCover`; the rep keeps their own hours and only moves to the Phase 1 queue). It does not touch the late-shift rule, and days a lead edited by hand are not flagged. Leads (anyone with the Lead role) are never offered as cover. Nobody already used as cover on that night or in that block (late, Phase 1 queue or anchor) is offered again, so one person never gets two jobs. Cover dropdowns only list reps of the matching queue for that day: VIP cover lists VIP reps, Phase 1 cover lists Phase 1 reps, anchor shift cover (a VIP seat, for both the Late Shift and the Phase 1 gap) lists VIP reps, and the Phase 1 queue cover (a VIP rep moving to Phase 1) lists VIP reps. A VIP rep who is the block's Phase 1 person counts as a Phase 1 rep for those two weeks (and is not offered for VIP cover), and goes back to VIP when the block ends. The chosen person takes the late hours and the queue that is missing for that night, and a lead can Remove it. Covers are stored per date in the shared plan as `lateCover` and merge per date. Everyone sees which nights still need cover: the outline and tint on the week and month cards, with a badge that reads "Lead action" for people with lead access (Admins when gated, or the PIN on the ungated copy) and "Need coverage" for everyone else, so a teammate can volunteer; in the day view Members get the same needs as plain red text ("Need coverage. Can you take it? Tell a lead.") with no dropdowns or buttons. Only people with lead access get the dropdowns, Add cover and Remove buttons, the Open the sheet button and the needs-action chip. In the week and month views a night that still needs a lead (late shift missing a VIP or Phase 1 person, or a Support Line owner off with no backup cover) gets a red outline, a tint and a Lead action badge on the whole card, whatever filters are on. The badge tooltip says why. Nights that have passed are not flagged, and the highlight clears once cover is added.

The Phase 1 / Support Line tab (gid 274979110, same workbook) is treated as always accurate. It has two parts, both read with the other sheets and saved quietly as `sheetPlan`. First, the four-week Support Line rotation: each block lists who covers the three line slots in order (6–10pm, 10pm–1am, 1–4am in standard time, which is 5–9pm, 9pm–12am, 12–3am on the summer schedule) plus a backup. On weekdays inside a block the rotation replaces the line bars; the slot times are fixed in the page, only the names come from the sheet. Second, the table at the top with current shift hours and breaks for the people listed (Qasim, Ayeshah, Schanzae, Ivan at the time of writing); those override the roster for those people on every date. The tab's clock is that of the current season, so the page takes the standard-time hour back off using today's date. Days someone edited by hand keep their own edit. When a line slot owner is off, the sheet's backup takes that slot automatically, and if the slot is already inside their shift only the Support Line bar is added and the shift is left alone. Only when it is not inside does the whole shift move (same length, same break position) to cover it. One backup can only take the slots that fit into a single shift, earliest first, and the rest show a red alert. Anyone who is covering shows "(covering)" in brackets after their name everywhere they appear (day view bars and Support Line bars, week lists, month lists), with the detail on hover, and the day view has a "Covering tonight" box at the top for everyone listing who is covering whom and what, for example "Qasim is covering Laraib on Support Line 6pm–10pm. Qasim's shift was adjusted to 6pm–3am to cover the Support Line." This covers the Support Line backup (also on hand-edited days, and when a lead placed a bar over an absent owner's slot), late-shift cover, the Phase 1 queue cover and anchor-shift cover, and it applies to Members too. Only when there is no backup, or the backup is off too, does a red alert appear and the Gaps row show the hole. A failed read keeps the last copy, including when only the rotation dates cannot be read (the date cells have appeared as both "Oct 5, 2026" and "Oct 5, 26"; both are accepted). Dates on all sheet tabs go through one reader (`parseAnyDate`) that accepts month-name, day-first, ISO, slash and dot forms with 2- or 4-digit years, and date-only cells are read from their real value, not their display text. Slash dates are read month first unless the first number is over 12. People missing from the roster are skipped. Check that this tab still matches when the clocks change in March.

Anchor shifts: the VIP sheet names three shifts that must always be held: 5PM–2AM, 6PM–3AM and 8PM–5AM on its current (standard-time) clock. They are the three single-person shifts (Osaid, Raza, Jawad), which the page stores as summer-schedule slots 2, 4 and 8, so it follows DST by itself (the sheet's own anchor text is fixed and needs checking in March, like the Support Line tab). When a block's Late Shift person or Phase 1 person normally works one of them (their roster or sheet shift, before the block changes anything), that anchor is vacated for the block. Anchor Cover 1 (column K of the VIP Coverage Plan tab) covers the Late Shift person's gap and Anchor Cover 2 (column L) covers the Phase 1 person's gap; the team fills them in on the sheet, and the page only reads them (stored per block in `vipPlan` as `cover1` and `cover2`). For the block people there is no picker in the page: the sheet is where it is filled in. The cover person takes the vacated anchor's hours, with the VIP queue, on every weekday of the block; the Phase 1 person keeps their own hours. Until the cell is filled, leads see a red "Anchor shift … is uncovered" alert with an Open the sheet button (it opens the Shift Sheet on the VIP Coverage Plan tab) and the Lead action highlight; once filled, everyone sees "(covering)" tags and the Covering tonight box. This matches the sheet's own column J warning (checked against it). Days a lead edited by hand are not touched.

Saved nights (Access > Lead tools): lists the upcoming nights that were saved, says who differs from the sheet (apart from the late shift and Phase 1 coverage, which follow the sheet from next week on), and lets a lead put the chosen ones fully back on the sheet (confirm, then Undo). Copying a day to nights this week in a different two-week VIP Coverage Plan block asks first, because this week is not updated from the sheet and the copy would keep the source night's Late Shift and Phase 1 person.

Fix breaks on edited days (Access > Lead tools): a saved night keeps the break it was saved with, so this action brings the breaks on upcoming saved nights back to the usual ones (the sheet and roster, or 2am for the late shift) for people working their usual hours, never touching hours, roles, swaps or cover; it asks first and offers Undo. Changing someone's roster hours for everyone also updates saved nights, one hour later on standard-time nights (the same as for a month).

Late-shift break: whoever works the late shift (block Late Shift person, late cover, a command) always breaks at 2am PKT on the standard clock, 1am in summer (`LATE_BRK_REL`, seven half-hours after the start), not at their own break position. Someone covering another person through a command (`takeover`) takes that person's whole shift: hours, break and split as they were before any change that night (a named shift takes the break of whoever normally works it).

Late-shift cover and anchor shifts: when a lead puts someone who works an anchor shift (their roster or sheet shift is 5PM–2AM, 6PM–3AM or 8PM–5AM) on late-shift cover (`lateCover` `vip` or `phase1`) for a night, the anchor shift they leave is vacated for that night, the same as for the block people (`anchorGaps` gives it kind `cover`; someone who is already one of the block's vacated people is not counted twice; days edited by hand are not touched, as before). Until a lead picks someone, leads see the red alert "Anchor shift … VIP is uncovered. <person> is covering the late shift." with a list of working VIP reps (not leads, not already used as cover, and not on late hours) and Add cover; the pick is stored with that night's late cover as `lateCover[date].anchor = { <late-cover person>: <cover> }`, the cover takes the vacated anchor's hours with the VIP queue, and everyone sees "<cover> is covering <person> on the 6pm–3am VIP shift" and the (covering) tag. The pick is removed together with its late cover (or replaced late cover), and a lead can Remove it alone. The server logs it ("Added anchor shift cover … for … on …"). This adds to the Lead action highlight and the needs-action chip like any other open anchor. The calendar API reports it in `covers` and `needsCover` (`worker/src/covers.js` mirrors `anchorGaps` / `gapCover`).

Original shifts: on the `2. VIP Coverage Plan` and Phase 1 / Support Line tabs the row under the names is each person's ORIGINAL shift (the next row is the current one, then the break). Every read writes the originals straight into the roster (`parseOriginalRows`, `applyOriginals`; not before the first team sync, and quietly like other sheet data; the hours it applied are remembered in the plan as `sheetRoster` so the server does not log them as someone's edit), so the roster always matches the sheet and a lead's hand edit to those people's roster hours is replaced on the next read. "LATE SHIFT" means the late-shift hours. The sheet's break is used only when the original and current shift are the same. Anyone whose hours on a weekday (including hand-edited days) differ from their roster shift, and who is not already named as cover, gets "(covering)" with "is working X instead of their usual Y" on hover and in the Covering tonight box (`kind: "hours"` in `coveringFor`). People not on those two tabs keep their roster hours. The VIP Coverage Plan block's people are tagged "(Late Shift)" and "(Phase 1 Coverage)" instead of "(covering)" (`kind: "rotation"` in `coveringFor`, shown in the week, month and day views and kept out of the Covering tonight box). The roster is never changed by the rotation: the Phase 1 person moves to the Phase 1 group and colour for the block's days and goes back to VIP afterwards, and the Late Shift person works the late hours on VIP colour. Hand-edited days keep their own edit and show no rotation tag.

Sheet-read data (`vipPlan`, `sheetPlan`) carries a `readAt` stamp set only when its content changes, and the shared plan keeps whichever copy has the newer `readAt` instead of using the plan's edit time, so a stale copy can never put back an older version of the sheet.

## Standing rules

- Primary time is PKT. ET is the secondary label. Overnight hours stay on the start day. Sunday is closed.
- Sundays stay hidden until someone clicks Show Sundays. Show them only when local storage `coverage-calendar-show-closed` is `"1"`.
- Default role filters are Phase 1, VIP, and Support Line. Lead is off. Clear restores those three, not an empty set.
- Away is a separate multi-select for Off and PTO. Nothing is selected by default, so everyone shows. Select all checks both and shows only those people. Off is the holiday rotation. PTO is holiday PTO or approved leave.
- Names in a month cell are listed by shift start time, earliest first, then by name. People who are Off or PTO stay visible, red with a strikethrough (white in Night, black in Frost), at the end of the time group. The count on a time chip does not include them.
- Week columns show shift times as chips: time on the left, working headcount on the right. Support Line is a separate section at the bottom of each weekday, grouped by start time only. Saturday has no Support Line section.
- The day view is one timeline list, grouped Leads, then VIP, then Phase 1. Do not put Phase 1 and VIP side by side unless the user asks again. The day view has no header block (no Back button, title, subtitle or peak chips) because the top bar already shows the date and view switch. Rows are compact so the day fits with little scrolling. Today's night shows a red Now line with a PKT time pill (real PKT clock, refreshed every 30 seconds), and the timeline scrolls sideways to it on narrow screens.

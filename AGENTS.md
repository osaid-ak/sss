# Support Orbit (SSS)

Support-floor coverage calendar. One HTML file. The live page is https://shift-plan.autoleap-sss.workers.dev/ (Google sign-in required) and the header reads **Support Orbit**. The old GitHub Pages address, https://osaid-ak.github.io/sss/, only redirects there.

Read this file before changing the calendar. Update it in the same change when behavior, publish steps, or standing rules change.

## Files

- `coverage-calendar.html` is the working copy. It is not committed.
- `index.html` is only a redirect to the worker address (a copy of `worker/stub-index.html`). It no longer matches the working copy. Never put the calendar back into it: GitHub Pages is public.
- `serve-calendar.py` is a local server only. Do not commit it.
- `README.md` is the short tester note. Keep it consistent with this file.

## Publish

1. Edit `coverage-calendar.html`.
2. In the `worker` folder run `.\deploy.ps1`. It builds the protected copy (plan address and `SSS_GATED` swapped in) and uploads the worker.
3. Commit `AGENTS.md` and anything else that changed (the calendar file itself is not committed), then push `main`. Do not touch `index.html`.
4. Tell the user to hard-refresh with Ctrl+F5 on the worker address.

Test with a copy of the calendar pointed at a local stand-in (see "How the data is shared"), then deploy. Do not commit `coverage-calendar.html`, `serve-calendar.py`, `worker/seed-plan.json`, or secrets. On PowerShell, commit with `git commit -m "..."` and chain commands with `;`.

## Sign-in gate (Cloudflare Worker, in `worker/`)

Access is restricted to people on the allowed email list, who sign in with Google (Intercom sign-in was dropped: it is an app-install flow that regular teammates cannot authorize). The worker serves the calendar page and stores the shared plan in a Durable Object (`PlanStore`, one strongly consistent copy; mantledb is no longer used by the gated site because it went down once); nothing is served before sign-in. Secrets (Google client ID and secret, session secret, allowed emails, admin emails, Super Admin email) are Cloudflare secrets, never in the repo or in chat. `worker/README.md` has the setup. `worker/deploy.ps1` builds `worker/public/index.html` from `coverage-calendar.html` (swapping the plan address for `/api/team/plan` and setting `SSS_GATED = true`, which also makes the page send the plan in one piece) and deploys; `worker/public/` is not committed. Run `node worker/test.mjs` after changing the worker.

Roles when gated: Member (no Access button, no lead tools), Admin (lead access without the PIN, plus Users under Access to add people as Members, remove Members and change Members' roles; added and removed people are kept in the ROLES store on top of `ALLOWED_EMAILS`) and Super Admin (one or more people, the secret `SUPER_ADMIN` is a comma-separated list; the only ones who can add an Admin or change or remove an Admin). Everyone signed in gets a Sign out button in the header. Sessions are signed cookies (7 days), not a server-side list; each deploy sets a new `BUILD_ID` (`deploy.ps1` passes it with `--var`) that is inside the cookie, so every deploy signs everyone out and they sign in with Google again (an open tab goes straight to the sign-in page within about 15 seconds: the page wraps etch so any own-API call that answers 401 redirects to /, and a 15-second /api/me check also runs when the tab becomes visible; the stale cookie is cleared; the activity log gets one "deploy" line by System when the first old session is met, and a "session ended" line with the person's name and email as each one is). Local data in the browser (the plan copy, backups, theme) is not a cookie and is kept; the worker keeps an activity log of the latest 1000 events (sign-in, refused sign-in, sign-out, user added, removed or role changed, and every schedule edit) in the ROLES store, readable by Admins under Access > Activity log. Every entry carries the person's name (made from their email, for example muhammad.jawad becomes Muhammad Jawad) and email. Schedule edits are worked out on the server on every plan save by comparing the new plan with the stored one, so they are logged whoever or whatever sends them: roster changes, hours and break changes, role changes, leave requests and their approval, decline or cancellation, holiday plans created, changed or deleted, late-shift and Phase 1 cover added or removed, and a weekday edited by hand or reset to default. Data that comes from the Google Sheet (VIP blocks, Support Line rotation and hours, Saturday names) is never logged as an edit, nor are roster hours taken from the sheet's original shifts. An import or restore shows as one Large change line. One limit: a save is attributed to whoever's browser sent it, so edits another person made offline and that were merged in by a later save are credited to that later sender. Each entry holds email, event, time, country, IP address and browser (User-Agent, shortened to 200 characters); these are personal data of teammates, so only Admins can read them and they are never shown to Members. The log has a search box that filters live from 2 characters on (several words must all match) across everything shown in a row: time, event, email, detail, IP, browser, country. The panel shows a short label such as "Chrome on Windows" with the full browser string on hover. The IP and browser fields are there so a future mobile app's sign-ins can be told apart. The server decides the role (`/api/me`) and enforces role changes. `SSS_GATED` stays `false` in the committed file; the PIN flow still applies to the ungated GitHub Pages copy.

The gate is live: the calendar and the plan are only served after Google sign-in, the plan is stored in the worker, and `index.html` on GitHub Pages is a redirect. A browser with no plan of its own shows "No team plan yet" (never the starter data) when the store is empty, and an Admin starts it with Import plan file. The old mantledb plan was overwritten with a placeholder (its three parts emptied) on 17 Nov 2026; the old data is still in the git history, so making the repo private is optional. Never open `coverage-calendar.html` directly with a local plan: its ungated copy still points at mantledb (`deploy.ps1` swaps that address), so test with a copy pointed at a local stand-in.

## Read API for automations (Intercom team moves)

`GET /api/v1/intercom-plan?from=YYYY-MM-DD&days=N` on the worker (`worker/src/intercom.js`, route `automationApi` in `worker/src/index.js`). It uses an API key (`Authorization: Bearer`), not a Google sign-in: the secret `API_KEYS` holds comma-separated `label:key` pairs (one per automation, removing a pair revokes it; keys are compared as hashes, never logged or returned; a refused call is logged as "api refused", at most once every 10 minutes). It is read only, never cached, and has no Intercom token: the Intercom automation (a separate Cloud Run project) stays the only writer. It does not follow the Google sign-in, the build-id session end or the roles.

It reports per shift day (the date it starts on, 15:00 PKT to 15:00 PKT) only the *decisions* leads made: people whose Phase 1 / VIP queue differs from normal (roster queue, with the sheet rotation's Phase 1 person on Phase 1, Monday to Friday). Sources, in the page's own order: the sheet's rotation and anchor cover, then late shift cover (`vip`, `phase1`), the Phase 1 queue cover (`p1q`), the commands from Slack, and last the roles a lead edited on that night (an override). A Saturday has no rotation and nobody moves unless the Weekend Cover names them: everyone it names is a decision with that queue (the rotation person goes to VIP only if named as a VIP rep, otherwise stays on Phase 1). Sunday never has decisions. Every call reads the Weekend Cover and VIP Coverage Plan tabs from Google itself (`worker/src/sheets.js`, the page's own reader, compared with it on the live tabs; the sheet must be readable by link) so nothing depends on an open browser, falling back per tab to the plan's stored copy and saying so in `sources`. Each day also carries `queues`, the calendar's full picture (every roster person's queue, rotation included; null on a Sunday), used only as a cross-check: the automation acts on `decisions`, on top of its own live sheet read (sheet = intended state, the calendar's changes win, hourly, acting on changes; see `handoff/intercom/README.md`). Decisions and the roster carry an `email` (the roster entry's own `email` field, else the one allowed email containing the name, else null) so the automation can verify the Intercom ID before moving anyone. `sheets.js` must be kept in step with the page's `parseWeekendRows` / `parseVipPlanRows` / `parseAnyDate`. Each day also carries who is off (`away`), who covers whom with exact times (`covers`, the same sentences as the page's Covering tonight box), what still needs a lead (`needsCover`, the page's red alerts) and the block's Late Shift person (`lateShift`), worked out by `worker/src/covers.js`, a function-by-function port of the page's `resolveDay`, `coveringFor`, the late-shift/anchor/Support Line logic and the leave and holiday rules; it also reads the Phase 1 / Support Line tab live (`parseSheetTab` in `sheets.js`). Any change to those page functions (or to `parseWeekendRows`, `parseVipPlanRows`, `parseSheetPlanRows`, `parseOriginalRows`, `parseAnyDate`) must be mirrored there and re-verified by comparing the worker with the page in the browser: build a test copy of the calendar with the worker modules bundled in and the page's `resolveDay` / `coveringFor` exposed, then compare covers, away and the lead alerts (read from the rendered day view) over a real plan and over randomised plans (leave, holidays, late/queue/anchor covers, hand edits, Support Line rotation, shift hours), across a clock change. The last run (13 plans, about 1,900 covers of all five kinds) had no differences. Anything that changes the queue logic in `resolveDay` / `applyLateCover` / `applyVipBlock` must be mirrored in `dayPlan` (`worker/src/intercom.js`) and checked against the page again (the `worker/test.mjs` API checks, plus comparing `dayPlan` with `resolveDay` over a real plan in the browser). `handoff/intercom/` is the package for that other project (contract, tested Python module, rollout); keep it in step with the API.

## Commands that change the calendar (Slack `/calendar`)

Leads change the calendar from Slack with `/calendar ...` (the Slack bot lives in the separate Intercom Phase Assignment project; `handoff/slack-calendar/` is its brief, with the JSON schema and 29 golden phrases that the worker's tests run). The worker does the work: `worker/src/commands.js` (validate, preview, apply, undo), `worker/src/dates.js` (dates in words, deterministic: `20th Nov to 25th Nov`, `from coming Monday to Thursday`, `this week and next`, ...), and the routes `POST /api/v1/calendar/command` and `/api/v1/calendar/undo` in `index.js`. They use a **write key** (secret `WRITE_KEYS`, same `label:key` format as `API_KEYS`; a read key cannot write and a write key cannot read) plus the asker's email (`actor.email`), and the asker must be allowed in AND an Admin or the Super Admin (checked again on the server). A request is a **preview** unless it says `dryRun: false`; applying needs a `commandId` (a repeat returns the stored result, nothing twice) and may carry the preview's `previewHash` (a mismatch applies nothing). The write is conditional on the plan version it was made from (`X-Expect-Updated-At`, retried up to three times), so it never overwrites a browser's save. Each command's undo record and result are kept in the plan store (`kv/undo-<id>`, `kv/cmd-<id>`), and `/calendar undo` takes back exactly what it added. The Google Sheet is never written, by anything.

What it writes, only for the nights named: approved **leave** (`off`; `back` splits and cancels), the calendar's own cover slots (`lateCover` late / Phase 1 / `p1q` / `anchor`), and **per-night changes** in the plan as `changes[date] = [{ id, cmd, type, ..., by, via, at }]`: `queue` (works Phase 1, VIP or both), `shift` (late shift, an anchor, or hours), `takeover` (works another person's queue and shift, optionally a named shift such as the 6pm anchor: that also fills the anchor the covered person left) and `swap` (two people exchange shifts and queues; the command records what each had at that moment, covers and hand edits included, as `now`, and any hand edit that was already there as `edited`, so the swap gives exactly the shift the other person has now and the old edit is not put back on top of it (`dropFoldedEdits`); an edit made after the swap still wins; a swap without `now`, from before this, swaps the night as built). The Support Line goes with the shift: a swap exchanges the two people's line slots, and a takeover of a whole shift (no named shift, or one with the same hours) takes the covered person's slots (`moveLine` in `applyChanges`; the backup does not move then). On a night whose bars a lead arranged by hand, the command records their signature as `fold` and the move is applied to those bars too; a later edit of the bars is taken as it is. The command summary says which slots changed hands ("Support Line: Laraib's 6pm–10pm slot goes to Ayeshah Tue 24 Nov."), only when one moves (`withLineMoves` in `commands.js`). Leads can also swap from the day view: a "Swap" button (Updates Today, Swap, Copy Day, Reset Default sit together; weekday nights that have not passed, leads only, refused while editing) opens a dialog with two people who are working that night (leads and people already moved that night are not offered, with a preview of what each takes); it writes the same `swap` change the command does (`now`, `edited`, `fold`, `by` from the signed-in email, `via: "Calendar"`), with an Undo toast and the usual Remove button. The Support Line slots of a swapped person show "(Swap)" too (week list and day bars, `lineTag`). Copy Day never copies the people a command moved on the source night, and leaves the people a command moved on a target night alone. They are applied last when a night is built (`applyChanges`, after the sheet, the block, the covers), on every night, and never change the roster; an override a lead set on that night still comes after them. Nothing is built into a saved night, so a swap is never applied twice and removing a change takes it away from the night. Leads see each change under the day's alerts as "Moved by <name> via Slack: ..." with a Remove button; everyone sees "(Swap)" for the two people of a swap (hover: "Swapped shifts with <name>: working ... instead of their usual ...", also in the Covering tonight sentences and as `label: "Swap"` on the API's `covers`), "(Moved)" for other changes and "(Covering)" and the Covering tonight sentences; anything still open is shown by the usual red Lead action alerts (a moved anchor person's open anchor, a late shift without a Phase 1 person, ...). Shifts and swaps are refused on Saturdays (the Weekend Cover sheet rules them; marking someone off on a Saturday is allowed and says the spot needs a name on the sheet), Sundays and past nights are skipped, leads are not used as cover, a person who is off cannot cover, and one person never gets two jobs a night. The activity log records `calendar command` and the individual `plan edit` lines under the asker's name with `via: Slack` (the lines are never collapsed to "Large change").

`dayPlan`, `covers.js` and `commands.js` mirror the page's `applyChanges`, `anchorGaps` / `gapCover` and `coveringFor`; the page and the worker were compared over randomised plans with every change type (about 2,200 covers, 9,500 queue checks, no differences, across the clock changes). Re-run that comparison after changing any of them (see the Read API section).

Tests: in `worker`, `npm test` runs `test.mjs` (the worker and its API) and `compare.mjs` (the calendar page's own script, loaded in a Node vm by `tools/page-vm.mjs`, against the worker's port on random plans: hours, breaks, queues, who is off, who covers whom and what still needs a lead, plus that converting old saved nights, editing and copying behave; it needs the page file and is skipped without it). Change the page or `covers.js` / `intercom.js`, then run it; a difference means the two drifted.

## How the data is shared

All three tabs are read by one JSONP reader (`fetchGvizRows`); the old Apps Script and same-origin weekend fallbacks are gone. Sheet updates and hand edits: the page re-reads all three sheet tabs when it opens, every 45 seconds while the tab is visible, as soon as the tab becomes visible again, every 20 seconds while the Shift Sheet panel is open, and when that panel closes (so a change on the sheet shows within about a minute on every open calendar, and the shared plan then carries it to the others). **A saved weekday keeps only what a lead changed on it** (stored as `days[date] = { v: 2, ovr: { <name>: { start, len, brk, split, roles, c } }, lines }`; Saturdays keep their own snapshot because the Weekend Cover sheet rebuilds them). A night is built like any other night: the sheet's hours, breaks and rotation, the block's Late Shift and Phase 1 person, the anchor cover, confirmed holiday plan hours, a lead's late-shift and Phase 1 covers, the commands from Slack; the overrides are applied last (`buildNight`, `applyEdits`). So everything a lead did not edit follows the sheet, including the late shift and Phase 1 coverage, the anchor checks, the "(Late Shift)" / "(Phase 1)" tags, breaks, the Support Line rotation and a roster hours change; a person with an override keeps exactly the fields that were edited and carries no rotation tag. `lines` (the Support Line bars) is only stored when a lead edited them. `c: 1` marks an override that came from copying a day (a later copy replaces it; a direct edit is never replaced). Editing in the page works on a working copy of the night (`ensureDay`); `persist()` stores only the people and fields that differ from the night as the sheet gives it (`commitWorking`, `commitNight`), so an edit equal to the sheet leaves nothing behind. Nights saved by older versions (`people`, `lineBars`, `baked`, `touched`, `rot`) are read through `legacyEdits`: what differs from the night as the sheet gives it becomes the overrides; the rotation people follow the sheet, this week included, a break that merely differs is not an edit unless it was edited directly (`touched`), and the Support Line follows the sheet's rotation. The first lead who opens the calendar converts them for good (`migrateSavedNights`, sets `schema: 4`; plans converted by the first version (`schema: 2`) are cleaned once by `reconcileThisWeek`, which drops the rotation people's overrides and the pinned Support Line bars from this week on; and every plan below schema 4 gets `adoptCoversFromEdits` once: from this week on, hours moved by hand that are really a cover become one (the person on the late hours while the block's Late Shift person is away is `lateCover.vip`, the person on the anchor hours a late-shift cover person left is its `anchor` pick), and hours pinned for a late-shift cover person are dropped because the cover decides them, so the break is the right one (the vacated person's for an anchor cover, 2am for the late shift) and nothing is left to ask a lead. Adding a cover from the day view does the same for that person's hand-moved hours. A night saved by an older version keeps a person as a lead's cover, not as the rotation, when the block's person is away or the anchor's holder moved elsewhere, and a person who is late-shift cover that night is never an override; the activity log gets one "Saved nights upgraded" line). The worker reads both forms with the same rules (`covers.js`: `nightEdits`, `legacyEdits`, `buildNight`). Confirmed holiday plans are a layer of the night (`applyHolidayHours`), not a snapshot; a roster hours change for everyone only changes the roster, and for one month it is stored as overrides for that person. Saturdays are the exception: the names come from the Weekend Cover sheet and the shift hours are always rebuilt from the product windows, so a hand edit to a Saturday's hours is not kept. Leave, holiday plans, roster edits and covers a lead added are never touched by the sheet.

Edits sync through the shared plan named `TEAM_PLAN` in the calendar file. A browser also keeps a local copy. Do not describe the calendar as Export/Import only.

Removing someone from the roster records them in the plan's `removed` list (name and time). Every merge and load drops those names from the roster, the default Support Line bars and the edited nights (overrides and the older snapshots), so an older copy in another browser cannot bring them back (the three-way merge alone would, when that browser has no sync base). Adding the same name again clears the entry. Saturdays follow the Weekend Cover sheet, so a name still on that sheet still shows on Saturdays until the sheet is changed; leave history stays.

Safety rule: a browser that has no plan of its own must adopt the team plan exactly on first contact, and data read from the Google Sheet (weekend names, VIP blocks) is saved quietly without counting as a team edit. Never let anything bump `updatedAt` or push before the first team sync finishes, because built-in default names and hours would then overwrite the team's roster. When testing, never load the live page from a fresh browser such as the preview pane. Use a copy pointed at a local stand-in for the team plan.

Each browser keeps up to 5 automatic backups (local storage key `coverage-calendar-backups`), taken before a teammate or merged update (at most every 15 minutes) and before a JSON import or restore. Lead tools has Restore backup. Import asks for confirmation because it replaces the shared plan. Browser panes that block storage skip backups silently.

Always read the Actual Cover columns on the sheet, not Planned. Actual updates itself when a swap happens. Swap, then Planned, only fill in when Actual is blank. Saturday names come from the Weekend Cover sheet. On Saturdays the Phase 1 rep works the full 6 hours with no break (stored as a break just past the shift end, which the page does not draw or count), and the VIP reps never break together: the first at the middle of the shift, each next one an hour later, in the order the sheet lists them. The sheet has no time columns. The product windows are Phase 1 8pm–2am and VIP 5pm–2am. Display re-applies those windows, then adds one hour on standard-time dates. Do not make that spreadsheet world-editable. Do not rewrite stored clocks unless the user asks.

The `2. VIP Coverage Plan` tab (gid 1563923804, same workbook) lists two-week Monday to Friday blocks. Each block names one VIP person on Late Shift and one on Phase 1, read from Actual Cover, plus the two anchor cover names from the Anchor 1 and Anchor 2 columns. The page polls it with the weekend sheet and stores the blocks in the shared plan as `vipPlan`. On weekdays inside a block, the Late Shift person works 9:30pm–6:30am PKT (10:30pm–7:30am on standard-time dates), keeping their usual break offset, and the Phase 1 person moves from VIP to Phase 1 for the whole shift. A person edited directly on a night keeps their own edit. Saturdays and Sundays are not affected. A failed read keeps the last blocks.

Every weekday late shift (anyone starting at 9:30pm PKT, or 10:30pm on standard-time dates, or later) needs one working VIP person and one working Phase 1 person. People who are Off or PTO do not count. When one is missing, the day view shows a red alert above the timeline naming who is off, and the month and week cells for that day show the red gap tint. With lead access the alert has a dropdown and Add cover button. Phase 1 queue cover is separate from the late shift: if the Phase 1 person the VIP Coverage Plan names is off, the day shows a Phase 1 needs cover alert and the Lead action highlight until a lead adds a VIP rep to Phase 1 (stored as `p1q` in `lateCover`; the rep keeps their own hours and only moves to the Phase 1 queue). It does not touch the late-shift rule, and a Phase 1 person a lead edited directly on that night is theirs to handle (not flagged). Leads (anyone with the Lead role) are never offered as cover. Nobody already used as cover on that night or in that block (late, Phase 1 queue or anchor) is offered again, so one person never gets two jobs. Cover dropdowns only list reps of the matching queue for that day: VIP cover lists VIP reps, Phase 1 cover lists Phase 1 reps, anchor shift cover (a VIP seat, for both the Late Shift and the Phase 1 gap) lists VIP reps, and the Phase 1 queue cover (a VIP rep moving to Phase 1) lists VIP reps. A VIP rep who is the block's Phase 1 person counts as a Phase 1 rep for those two weeks (and is not offered for VIP cover), and goes back to VIP when the block ends. The chosen person takes the late hours and the queue that is missing for that night, and a lead can Remove it. Covers are stored per date in the shared plan as `lateCover` and merge per date. Everyone sees which nights still need cover: the outline and tint on the week and month cards, with a badge that reads "Lead action" for people with lead access (Admins when gated, or the PIN on the ungated copy) and "Need coverage" for everyone else, so a teammate can volunteer; in the day view Members get the same needs as plain red text ("Need coverage. Can you take it? Tell a lead.") with no dropdowns or buttons. Only people with lead access get the dropdowns, Add cover and Remove buttons and the Open the sheet button. In the week and month views a night that still needs a lead (late shift missing a VIP or Phase 1 person, or a Support Line owner off with no backup cover) gets a red outline, a tint and a Lead action badge on the whole card, whatever filters are on. The badge tooltip says why. Nights that have passed are not flagged, and the highlight clears once cover is added.

The Phase 1 / Support Line tab (gid 274979110, same workbook) is treated as always accurate. It has two parts, both read with the other sheets and saved quietly as `sheetPlan`. First, the four-week Support Line rotation: each block lists who covers the three line slots in order (6–10pm, 10pm–1am, 1–4am in standard time, which is 5–9pm, 9pm–12am, 12–3am on the summer schedule) plus a backup. On weekdays inside a block the rotation replaces the line bars; the slot times are fixed in the page, only the names come from the sheet. Second, the table at the top with current shift hours and breaks for the people listed (Qasim, Ayeshah, Schanzae, Ivan at the time of writing); those override the roster for those people on every date. The tab's clock is that of the current season, so the page takes the standard-time hour back off using today's date. A person edited directly on a night keeps their own edit. When a line slot owner is off, the sheet's backup takes that slot automatically, and if the slot is already inside their shift only the Support Line bar is added and the shift is left alone. Only when it is not inside does the whole shift move (same length, same break position) to cover it. One backup can only take the slots that fit into a single shift, earliest first, and the rest show a red alert. **Break Rotations** (columns right of Backup, under the header "BREAK ROTATIONS"): the row below names the people (Zunair, Laraib, Qasim and Ayeshah at the time of writing) and each four-week block lists a break for each of them ("10 - 11" etc.), chosen so nobody breaks during their own line duty. The page reads each break inside that person's shift (the table's hours, else the roster's), puts it on the summer schedule like the other sheet times (`parseSheetPlanRows`, `breaks` on each block of `sheetPlan.line`; the worker's `parseSheetTab` does the same) and applies it on every weekday of the block after the table's hours (`applySheetPlan`), so it replaces the table's break for those people on those dates; a direct edit on a night still wins. Anyone who is covering shows "(Covering)" in brackets after their name everywhere they appear (day view bars and Support Line bars, week lists, month lists), with the detail on hover, and the day view has a "Covering tonight" box at the top for everyone listing who is covering whom and what, for example "Qasim is covering Laraib on Support Line 6pm–10pm. Qasim's shift was adjusted to 6pm–3am to cover the Support Line." This covers the Support Line backup (also on nights with edits, and when a lead placed a bar over an absent owner's slot), late-shift cover, the Phase 1 queue cover and anchor-shift cover, and it applies to Members too. Only when there is no backup, or the backup is off too, does a red alert appear and the Gaps row show the hole. A failed read keeps the last copy, including when only the rotation dates cannot be read (the date cells have appeared as both "Oct 5, 2026" and "Oct 5, 26"; both are accepted). Dates on all sheet tabs go through one reader (`parseAnyDate`) that accepts month-name, day-first, ISO, slash and dot forms with 2- or 4-digit years, and date-only cells are read from their real value, not their display text. Slash dates are read month first unless the first number is over 12. People missing from the roster are skipped. Check that this tab still matches when the clocks change in March.

Anchor shifts: the VIP sheet names three shifts that must always be held: 5PM–2AM, 6PM–3AM and 8PM–5AM on its current (standard-time) clock. They are the three single-person shifts (Osaid, Raza, Jawad), which the page stores as summer-schedule slots 2, 4 and 8, so it follows DST by itself (the sheet's own anchor text is fixed and needs checking in March, like the Support Line tab). When a block's Late Shift person or Phase 1 person normally works one of them (their roster or sheet shift, before the block changes anything), that anchor is vacated for the block. Anchor Cover 1 (column K of the VIP Coverage Plan tab) covers the Late Shift person's gap and Anchor Cover 2 (column L) covers the Phase 1 person's gap; the team fills them in on the sheet, and the page only reads them (stored per block in `vipPlan` as `cover1` and `cover2`). For the block people there is no picker in the page: the sheet is where it is filled in. The cover person takes the vacated anchor's hours, with the VIP queue, on every weekday of the block; the Phase 1 person keeps their own hours. Until the cell is filled, leads see a red "Anchor shift … is uncovered" alert with an Open the sheet button (it opens the Shift Sheet on the VIP Coverage Plan tab) and the Lead action highlight; once filled, everyone sees "(Covering)" tags and the Covering tonight box. This matches the sheet's own column J warning (checked against it). A person edited directly on a night keeps their own edit.

Sync From Sheet (Access > Lead tools): a lead picks a start and end date (up to 63 nights); the sheet is read again, and those nights lose what was edited or copied onto them (`resetNightsToSheet`), so they show exactly the sheet's coverage and placements again; the late-shift and Phase 1 covers leads added on them are removed only when that box is ticked; leave, holiday plans and Slack commands are not touched; Undo restores everything. The calendar otherwise re-reads the sheet by itself (see above), so this is for resetting nights after edits.

Edited nights (Access > Lead tools): lists the upcoming nights that have overrides (who was edited and how, and whether it was copied), selects the copied ones by default, and lets a lead put the chosen ones fully back on the sheet (confirm, then Undo). The day view tells leads "Edited ✎ <names>. Everyone else follows the sheet." with a Reset Default button (outside edit mode it asks first and offers Undo).

Late-shift break: whoever works the late shift (block Late Shift person, late cover, a command) always breaks at 2am PKT on the standard clock, 1am in summer (`LATE_BRK_REL`, seven half-hours after the start), not at their own break position. Someone covering another person through a command (`takeover`) takes that person's whole shift: hours, break and split as they were before any change that night (a named shift takes the break of whoever normally works it).

Late-shift cover and anchor shifts: when a lead puts someone who works an anchor shift (their roster or sheet shift is 5PM–2AM, 6PM–3AM or 8PM–5AM) on late-shift cover (`lateCover` `vip` or `phase1`) for a night, the anchor shift they leave is vacated for that night, the same as for the block people (`anchorGaps` gives it kind `cover`; someone who is already one of the block's vacated people is not counted twice; a person edited directly on a night keeps their own edit). Until a lead picks someone, leads see the red alert "Anchor shift … VIP is uncovered. <person> is covering the late shift." with a list of working VIP reps (not leads, not already used as cover, and not on late hours) and Add cover; the pick is stored with that night's late cover as `lateCover[date].anchor = { <late-cover person>: <cover> }`, the cover takes the vacated anchor's hours with the VIP queue, and everyone sees "<cover> is covering <person> on the 6pm–3am VIP shift" and the (Covering) tag. The pick is removed together with its late cover (or replaced late cover), and a lead can Remove it alone. The server logs it ("Added anchor shift cover … for … on …"). This adds to the Lead action highlight and the needs-action chip like any other open anchor. The calendar API reports it in `covers` and `needsCover` (`worker/src/covers.js` mirrors `anchorGaps` / `gapCover`).

Original shifts: on the `2. VIP Coverage Plan` and Phase 1 / Support Line tabs the row under the names is each person's ORIGINAL shift (the next row is the current one, then the break). Every read writes the originals straight into the roster (`parseOriginalRows`, `applyOriginals`; not before the first team sync, and quietly like other sheet data; the hours it applied are remembered in the plan as `sheetRoster` so the server does not log them as someone's edit), so the roster always matches the sheet and a lead's hand edit to those people's roster hours is replaced on the next read. "LATE SHIFT" means the late-shift hours. The sheet's break is used only when the original and current shift are the same. Anyone whose hours on a weekday (including edited nights) differ from their roster shift, and who is not already named as cover, gets "(Covering)" with "is working X instead of their usual Y" on hover (when the hours are exactly the usual shift of somebody who is away in the same queue it says who: "is covering Qasim: working 7pm–4am instead of their usual 8pm–5am") and in the Covering tonight box (`kind: "hours"` in `coveringFor`). People not on those two tabs keep their roster hours. The VIP Coverage Plan block's people are tagged "(Late Shift)" and "(Phase 1)" instead of "(Covering)" (`kind: "rotation"` in `coveringFor`, shown in the week, month and day views and kept out of the Covering tonight box). The roster is never changed by the rotation: the Phase 1 person moves to the Phase 1 group and colour for the block's days and goes back to VIP afterwards, and the Late Shift person works the late hours on VIP colour. A person edited directly on a night keeps their own edit and shows no rotation tag.

Sheet-read data (`vipPlan`, `sheetPlan`) carries a `readAt` stamp set only when its content changes, and the shared plan keeps whichever copy has the newer `readAt` instead of using the plan's edit time, so a stale copy can never put back an older version of the sheet.

## Backups of the shared plan (server side)

Before a save replaces the plan, `PlanStore` keeps the plan as it was (`backUp` in `worker/src/index.js`; at most one copy every 30 minutes, skipped when unchanged and never able to fail a save). Every copy of the last 24 hours is kept, then the earliest of each day for 14 days (`backupsToKeep`). Admins read them at `GET /api/backups` (list) and `GET /api/backups/<id>` (one plan), and restore through Access > Restore Backup, which lists the server backups (Admins, gated) and this browser's own; a restore goes through the normal save, so the plan as it is then is backed up too. `worker/test.mjs` covers it. Keeping `coverage-calendar.html` itself in version control is still open (the repo is public; it would need a private repo or branch).

## Standing rules

- Primary time is PKT. ET is the secondary label. Overnight hours stay on the start day. Sunday is closed.
- Sundays stay hidden until someone clicks Show Sundays. Show them only when local storage `coverage-calendar-show-closed` is `"1"`.
- Default role filters are Phase 1, VIP, and Support Line. Lead is off. Clear restores those three, not an empty set.
- Away is a separate multi-select for Off and PTO. Nothing is selected by default, so everyone shows. Select all checks both and shows only those people. Off is the holiday rotation. PTO is holiday PTO or approved leave.
- Names in a month cell are listed by shift start time, earliest first, then by name. People who are Off or PTO stay visible, red with a strikethrough (white in Night, black in Frost), at the end of the time group. The count on a time chip does not include them.
- Week columns show shift times as chips: time on the left, working headcount on the right. Support Line is a separate section at the bottom of each weekday, grouped by start time only. Saturday has no Support Line section.
- The day view is one timeline list, grouped Leads, then VIP, then Phase 1. Do not put Phase 1 and VIP side by side unless the user asks again. The day view has no header block (no Back button, title, subtitle or peak chips) because the top bar already shows the date and view switch. Rows are compact so the day fits with little scrolling. Today's night shows a red Now line with a PKT time pill (real PKT clock, refreshed every 30 seconds), and the timeline scrolls sideways to it on narrow screens. A Gaps row under the peak band flags slots inside the peak window (Phase 1, VIP) and the Support Line window with 0 people (red) or 1 person (amber); it follows DST and is hidden on Saturdays and Sundays. Only a Saturday cover note and the edit-mode Reset button appear above the timeline.
- There is no Year view (removed); the views are Month, Week and Day. Users (Admins only) is in the account menu (initials button), above Sign out, not under Access.
- Print, Export (CSV), Export JSON and Save snapshot were removed (the page no longer has them or the code behind them, including the embedded-snapshot loading). The header has one Shift Sheet button that opens the whole Google Sheet workbook inside the calendar, starting on the Weekend Cover tab. Users switch tabs inside the sheet. It is an embedded editor, so edit rights follow the viewer's Google account, and an Open in Google Sheets link is the fallback. Back to calendar, Escape, or changing view closes it and re-reads the sheet; while open it re-reads every 20 seconds. There is no Sync sheet button: all sheet tabs are re-read automatically.
- DST is automatic and follows US Eastern time, because shifts are anchored to ET. Stored clocks are the summer (EDT) schedule. From the first Sunday of November to the second Sunday of March, every date shows its shifts, breaks, splits, line assignments and Saturday windows one hour later in PKT, and the Peak window (7pm–12am becomes 8pm–1am) and Support Line window (5pm–3am becomes 6pm–4am) move with them. The board itself stays 3pm–8am PKT in the data, but the day timeline starts at 4pm PKT (earlier only if somebody starts earlier; `dayStartSlot`, `T0`) so the empty first two hours take no room; the holiday planner keeps the whole board. There is no DST button, and `dst` in saved data is always false. Older plans saved with the global switch on are converted back to the summer schedule on load. Per-day edits are stored as shown for that day. Do not reintroduce a manual switch unless asked.
- The lead PIN is in the page source. Do not print it in chat or in the UI.

- UI regression check: every change that adds or alters something visible must be looked at on screen before it is published, not only syntax-checked. Check a desktop width and a phone width (375px), the Night and Frost themes, and long content (for example the user list with 15+ people, a day with many names). Panels that can grow (Users, Activity log, modals) keep their header and buttons fixed and scroll only the list, and must fit inside the window. Do this alongside the data checks, every time. Also page through many weeks, months and days (about 20 weeks, 20 months, 130 days, both directions) with an error listener on: a render that throws only on a week with leave or a Support Line owner off leaves the header on the new week and the grid on the old one.
- Month health markers: every upcoming weekday and covered Saturday cell has a small marker next to the date: a tick (covered all night), "!" (only one person on Phase 1 or VIP for part of the peak window) or a cross (nobody in part of the peak window, or a late shift missing a VIP or Phase 1 person). The shape carries the meaning as well as the colour, hovering gives the reason, and a legend sits under the grid. The Support Line is one person per slot by design, so it never tints a card or sets a marker; instead any stretch of the Support Line window with nobody on the line (an owner's break, or nobody scheduled) is a lead-only need: the day view says "Support Line has nobody 9pm–11pm. Adjust breaks or add cover.", the card gets the Lead action badge (leads only, never "Need coverage" for Members) and the API's `needsCover` lists it (`lineZeroRuns` in the page and `covers.js`). Past nights, closed days and Saturdays still waiting for Actual Cover get no marker. Everyone sees them.
- Interface rules: the header shows a red chip (just "! N" on phones) that opens a list of the next 31 days' nights that need cover, each opening that day: "N nights need action" for leads (everything they have to do, including an empty stretch on the Support Line) and "N nights need coverage" for everyone else (only what a teammate could volunteer for). When gated, the Theme button becomes an account button (initials) whose menu shows the email and role, the theme choice and Sign out. Messages use non-blocking toasts, not browser alerts; cover changes show an Undo toast; confirmations use the in-page dialog (`askConfirm`), except the unsaved-changes prompt, which stays native because it runs in synchronous close paths. A browser with no plan of its own shows "Loading the team plan…" (or a Try again card if it fails) instead of the built-in starter data, and never edits until the first team sync finishes. The first visit follows the device's light or dark setting. Keep every text colour at 4.5:1 contrast or better in both themes (Frost values were darkened for this) and keep the visible keyboard focus outline. Dialogs have `role="dialog"`, and Escape closes them. On phones, month and day views swipe left or right to change month or day (week view and the day timeline scroll sideways instead), and buttons are at least 38 to 40px tall.
- Copy day: leads see a "Copy Day" button above the day view on every weekday (not Saturdays, which follow the sheet). Quick picks: This week, Next week, Next 4 weeks, Next 2 weeks from this day, Next 4 weeks from this day (the weekdays in the 14 or 28 days after the copied night, ending on the last Friday inside that span, never spilling into the next week), Rest of this week, Same weekday next 4 weeks, Every weekday next 4 weeks, Clear, and a grid of weekdays by week (8 weeks, Show 4 more weeks) where each day can be ticked. Past nights, Saturdays, Sundays and the source day are not offered; nights that already have edits are marked ✎ and copying asks before replacing them. A copy stores, on each target night, only what differs from that night as the sheet gives it, taken from the source night as shown (shifts, breaks, roles, and the Support Line bars only if the source's were edited), marked `c: 1`; it is moved by the hour across a clock change so the ET hours stay the same. It never copies leave, a lead's covers, or the Late Shift, Phase 1 and anchor cover people of the source or of the target (they follow each night's own block), and it never overwrites what was edited directly on a target night (the dialog and the toast say so). A toast offers Undo, and the server logs one "Edited the schedule for …" line per night (or one Large change line above 15).
- Tab icon: a rounded square showing today's date (the shift day, which changes at 08:00 PKT like the header's "Night of"), drawn as an SVG by `updateFavicon`: a single-colour rounded square (`FAVICON_COLOR`, coral) with the date in white, like Google Calendar's. The header shows the Support Orbit logo (an embedded PNG with a transparent background, so it works on both themes; its alt text is "Support Orbit") with no tag after it.
- Edit: the pencil "Edit" button sits in the nav beside Hide Sundays (it turns into a red "Done" while editing) and is shown only to Admins (or the PIN holder on the ungated copy); it is no longer in the Access menu.
- Day view: the "Covering tonight" box and the leads' "Edited ✎ … Everyone else follows the sheet" note are not on the page; they sit in an "Updates Today" popover (a button with a count, shown to everyone when there is something to say) that opens on click and closes on a click outside or Escape. Updates Today, Copy Day and Reset Default sit at the right end of the filter row at the top (`dayToolsHtml`, bound by `bindDayTools` whenever the filter row is drawn). The red Lead action alerts stay on the page. The timeline has no horizontal scroll: it squeezes or stretches to the window (also with browser zoom; hour labels thin out to every second hour when narrow); only phones (under 640px) keep a minimum column width and scroll sideways to the Now line.
- Status and clock pill: a floating pill fixed at the bottom right (bottom centre on phones) shows the sync status (the Live chip, as a dot and word), PKT and ET (always labelled "ET", never EST or EDT), refreshed every 5 seconds (`updateClock`). It never takes a click (`pointer-events: none`), sits under dialogs and toasts, is hidden while the Shift Sheet panel is open, and `main` has extra bottom padding so content scrolls clear of it. The Access button and the other main buttons use the logo red (`--brand`; Frost uses a darker red for contrast); green stays for the Phase 1 role. The sign-in page is centred both ways, shows the logo at its natural proportions and a "Powered by" signature under the button (`worker/src/logo.js`).
- Who is viewing (gated only): a strip of overlapping initial circles left of Shift Sheet, like Google Sheets. Every open tab posts to `POST /api/presence` every 20 seconds (`{tab, state}`; `state` is `active`, `idle` or `gone` on pagehide); a tab is idle after 2 minutes without mouse, keys, touch or scroll, or while hidden (`startPresence` in the page). The worker keeps it in memory in `PlanStore` (`beat`, `/presence`; an entry drops off after 100 seconds, nothing is stored or logged) and answers with everyone present (name from the email, email, state; a person with several tabs counts once, active wins). It is shown to everybody who is signed in, hides you and the whole strip when nobody else is here, shows 4 circles (2 on phones) plus "+N", idle ones faded with an amber dot (active green); click opens the "Viewing now" list.
- Somebody who is away (OOO, off, PTO or sick) is never shown as covering: `coveringFor` drops every cover entry for an away person (the "(Covering)" tag, the hover text, the Covering tonight sentences and the API `covers`); only the sheet rotation tags "(Late Shift)" / "(Phase 1)" stay. `covers.js` does the same.
- Off sick: a leave has an optional `sick: true` (Add Leave and Mark OOO both have a "Sick 🤒" checkbox; the Slack/API op `off` takes `sick: true`, `worker/src/commands.js`). Wherever a name is crossed out or dimmed as away (month and week lists, the Off list, the day view row and its tag, which then reads "Sick") it gets a 🤒 at the very end of the line, after the hours (in the day view at the end of the "Sick — not counted in coverage" tag), and hovering anywhere on that line says "Off sick" (plain leave says "Off"; never "Away") (`sickMark`, `sickOn`; the emoji sits in an inline-block span so the strikethrough does not cross it). The leave list shows it too, the read API lists such a person in `away` with `sick: true` (`covers.js` `sickOn`), and the activity log says "Added approved sick leave for …". Sick changes nothing about coverage: it is the same as any approved leave. Holiday-planner OFF/PTO cells have no sick option. `handoff/slack-calendar/` (schema, golden phrases, README) carries the flag.
- Side panel (`#siderail`, `renderRail` in `renderChrome`): Admins and Super Admins (the PIN holder on the ungated copy) get a left rail with Calendar, Resources and Reports; Members get nothing and their layout is unchanged. Calendar is the whole existing page. Resources and Reports are placeholders ("Nothing here yet") until their content is decided: they hide the calendar's view tabs, date navigation, filter bar and grid (`.app.sec-on`) and show `#sectionPane`; the header (Shift Sheet, account, Access) stays. The rail is 76px wide beside the page; under 640px it becomes a bottom bar and the status pill and toasts move above it. The current section is `ui.section` (not saved), switching away from the calendar is refused while editing, and a user who loses Admin goes back to Calendar.
- Calendar text (month, week, day and timeline) is one pixel larger than the original sizes, with the same layout. Keep that scale when adding new text.
